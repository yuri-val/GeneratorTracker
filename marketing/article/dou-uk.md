## Стек

- Expo SDK 57, React Native 0.86, React 19.2, TypeScript.
- AsyncStorage як локальне сховище, Firebase Auth + Firestore для необов'язкової синхронізації.
- iOS — нативні SwiftUI-форми через `@expo/ui` і системні таби з Liquid Glass; Android — Material 3; web лишився на React Native Paper.

## Принцип 1: джерело правди — телефон

Під час блекауту мобільний інтернет теж часто лежить. Тому всі операції йдуть у локальне сховище, а хмара — лише копія для інших пристроїв того ж користувача. UI ніколи не чекає мережі.

Усі записи в AsyncStorage проходять через один FIFO-м'ютекс. Без нього дві паралельні операції (наприклад, «стоп» і пул із хмари) читали одну версію даних і перезаписували зміни одна одної.

## Принцип 2: стан замість черги

Перша версія мала класичну чергу синхронізації: кожна зміна — запис у `@sync_queue`, яку потім розгрібаєш. На практиці черга розходилась із даними, а зміни, які тричі не вдалося відправити, просто відкидались — тобто тихо губились.

Зараз черги немає. Кожен створений чи змінений запис зберігається зі статусом `pending` і монотонним `lastModified`, який ставить сховище, а не той, хто викликає. Синхронізація просто бере все `pending`. Видалення записують **tombstone** — навіть коли користувач не залогінений, — щоб видалення колись дійшло до хмари і щоб пул ніколи не «воскресив» запис. Старі інсталяції мігрують автоматично: видалення з черги стають tombstones, зміни — `pending`.

## Синхронізація: спочатку push, потім pull

`performFullSync` — це push, а потім pull, і ніколи два одночасно:

1. **Push:** tombstones → видалення в хмарі (генератор разом з усіма підколекціями), потім генератори, потім дочірні записи тих генераторів, що вже є в хмарі. Успішні записи позначаються synced, лише якщо їх не редагували, поки йшов запит. Невдалі лишаються `pending` до наступної синхронізації.
2. **Pull:** повний знімок через `getDocsFromServer` (дочірні колекції раніше за генератори) і злиття чистою функцією.

Усі мережеві виклики мають тайм-аут 30 с — Firestore у поганій мережі вміє «висіти» дуже довго.

## Правила злиття

Найважливіше рішення — винести злиття в чисту функцію без I/O. Правила:

- **Last write wins** за клієнтським ISO `lastModified`. Firestore зберігає клієнтський час без змін (серверний — окремо, у `serverUpdatedAt`), документи пишуться повним `set`, щоб очищені поля теж доходили.
- **Рівні часи** означають, що віддалена копія — це та сама версія, і локальний запис стає synced.
- **Локальний tombstone завжди перемагає** — запис, видалений на цьому пристрої, не повертається.
- **Віддалене видалення теж перемагає**, але відсутність у знімку видаляє лише ті записи, що точно були в хмарі *цього* акаунта (`userId === uid` і синхронізовані до моменту знімка). Інакше новий локальний запис або дані іншого акаунта зникли б.
- **Сироти** — дочірні записи без генератора, які лишили старі версії, — не зберігаються.

Ось як це виглядає в коді (`src/services/syncMerge.ts`):

```ts
const isConfirmedInCloud = (record: SyncEntity, ctx: MergeContext): boolean => {
  if (record.userId !== ctx.uid) return false;
  if (record.syncedAt) return compareTimestamps(record.syncedAt, ctx.snapshotTime) < 0;
  return record.syncStatus === 'synced';
};
```

Realtime-слухачі `onSnapshot` застосовують додавання/зміни/видалення, а перший *серверний* знімок кожного слухача звіряє видалення, зроблені офлайн. Знімки лише з кешу ніколи нічого не видаляють — це була найпідступніша помилка: кеш після перевстановлення порожній, і «відсутність» у ньому не означає видалення.

## Як це тестувати

- Чисте злиття покрите юніт-тестами (Jest) — сценарії «локально/віддалено/tombstone/інший акаунт/сирота» без жодного мока мережі; оркестрація push/pull — окремими тестами з замоканим Firestore.
- e2e на Playwright проти web-збірки, окремий набір — з Firebase Auth/Firestore емуляторами, щоб синхронізація ганялась без продакшн-даних (режим емулятора примусово переключає на demo-проєкт).
- Тести правил безпеки Firestore на емуляторі.
- Maestro-сценарії для нативного UI на iOS і Android.

## Кілька граблів

- **Hermes не має `Intl.PluralRules`** — форми множини («1 година / 2 години / 5 годин») довелося рахувати вручну, хоча в браузері все працювало.
- **iOS 26:** аксесуар таб-бару не можна додавати умовно — SwiftUI перебудовує TabView і застосунок падає. Тому «живий» рядок активних генераторів — звичайний футер над таб-баром.
- **Вкладені `Pressable`** на web рендеряться як `<button>` у `<button>` — невалідний HTML і дивні кліки.
- Дві редакції (платна без реклами й безкоштовна з обмеженнями) збираються з однієї кодової бази: редакцію обирає `app.config.js` під час збірки, а екрани питають лише хук `useEntitlements()`.
